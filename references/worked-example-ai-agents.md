# 示范产物：AI Agent 领域

这是一份完整走完阶段 1 的产出，用作输出质量的对标基线。新建地图时对照检查：密度、锋利度、可证伪性是否在同一水位。

## 5 个核心心智模型

**1. Agent = 模型 + 工具 + 循环，循环才是本体**
定义：agent 是"模型在循环里持续决策"的系统，单次调用只是 pipeline。
反直觉点：能力瓶颈常在循环设计（能否暴露错误、能否重试），而不在模型强弱。
可证伪：如果换用更强的模型后成功率没提升，说明瓶颈在循环/工具/上下文，不在智能。

**2. 上下文窗口是 agent 的全部记忆，因此一切都是上下文工程**
定义：模型每次调用都失忆，它"记得"的一切都是本轮 prompt 里的 token；记忆、状态、反思本质都是"怎么把东西放回去"。
反直觉点：上下文是稀缺资源而非仓库，塞满会掉性能（中间段落最易被忽略）。
可证伪：如果你把资料从 20k 扩到 200k token 而准确率不升反降，说明密度问题大于覆盖问题。

**3. 工具是手，工具描述是写给模型看的 prompt**
定义：工具的 name/description/schema 是模型的决策依据，不是给人读的文档。
反直觉点：工具越多越不可靠，20 个工具会造成选择困难与参数错填；应渐进披露。
可证伪：如果给工具加一句"何时不要用我"就显著降低误用，说明此前的失败是描述问题而非能力问题。

**4. 自主性是一条光谱，不是开关**
定义：提示链 → 路由 → 并行 → 编排者 → 自主 agent，向右每格买到泛化、付出可预测性。
反直觉点：生产系统里绝大多数是"带 LLM 判断节点的确定性流程"，不是自主 agent。
可证伪：如果给一个已被 workflow 稳定解决的流程加上自主决策，失败率上升，说明自主性被过度使用。

**5. 错误会复利，而它不报错**
定义：0.95²⁰ ≈ 36%，30 步只剩 21%；且失败现场往往没有任何异常信号。
反直觉点：工程重点不是"更聪明"，而是"让错误可见、可停、可回滚"。
可证伪：如果加了轨迹日志与步数上限后成功率显著提升，说明此前的损失主要来自"错误未被发现"，而非"能力不足"。

## 3 个根本分歧

**分歧 1 · Workflow 还是 Agent**
A 方：失败必须可复现，否则无法测试、重试、估算成本。
B 方：真实任务分支无法预先枚举，写死流程只是把维护成本转给工程师。
裁决：看结果能否自动验证。代码能跑、SQL 能执行 → 放开自主；答案是文案或评估这类无法判对错的 → 用流程箍住。
裁决变量：**可验证性**。

**分歧 2 · 单 agent 大上下文，还是多 agent 分工**
A 方：子 agent 间不共享上下文，隐含决策会冲突（一个改了接口，另一个还在用旧的）。
B 方：并行即时间，且上下文隔离可防止无关信息干扰判断。
裁决：看耦合度。只交换最终产物 → 多 agent；共享隐含约定（同一代码库、同一设计）→ 单 agent。
裁决变量：**子任务耦合度**。

**分歧 3 · 瓶颈在模型，还是在脚手架**
A 方：新模型发布会吃掉一半脚手架，等模型比雕花划算。
B 方：同一模型在成熟 harness 里和裸 API 里是两个物种——模型不能改变自己的输入，而输入决定输出。
裁决：6-12 个月内脚手架收益更大；长期两者都被训练吸收。学原理和手写循环，别学框架 API。
裁决变量：**时间尺度**。

次级分歧（可作补充）：长上下文 vs RAG——塞得进就别建检索，塞不进或需频繁更新时才外置。

## 10 道诊断题

1. 一次 LLM 调用生成 SQL → 执行 → 返回。这是 agent 吗？依据是什么？（边界）
2. 第 30 步忘记目标、第 40 步重复劳动。给 3 种成因不同的修法与代价。（异常归因）
3. 3 个工具加到 23 个后准确率下降。从工具选择与上下文两角度解释，并设计不删工具也能验证假设的实验。（异常归因 + 评估）
4. 单步 0.97、平均 25 步，端到端是多少？要求 80% 时有哪些手段，分别作用在单步成功率还是步数上？（杠杆）
5. 举一个"用 agent 一定比写死逻辑更差"的场景，判断依据是哪个变量。（拒绝）
6. 为什么"让大模型打 1-5 分"是坏 eval？给一个可复现且能定位失败步骤的替代方案。（评估）
7. 从 200 份财报抽同一张表并汇总：workflow 还是 agent？并行还是串行？关键变量？（取舍）
8. 什么信号说明该拆成多 agent？什么信号说明拆错了？（裁决）
9. 短期记忆与长期记忆的边界画在哪？各给一个该写与绝对不该写的例子。（结构）
10. 只有 8k 上下文的弱模型，还用多步 agent 吗？架构怎么改？（约束设计）

## 48 小时动手路线（阶段 4 之后的延伸）

明确反对从 LangChain / LangGraph 起步——框架会把最该看清的 while 循环藏起来。

- 0-4h：50 行——一个工具、一次 function calling、最多 10 轮的循环
- 4-12h：工具加到 5 个，故意制造失败，观察错误处理（对应模型 3）
- 12-24h：20 条任务 + 自动判定，跑出基线（对应模型 5）
- 24-36h：同任务写一版纯 workflow 对照成功率/成本/耗时（亲手验证分歧 1）
- 36-48h：一页"该任务的失败模式清单"
